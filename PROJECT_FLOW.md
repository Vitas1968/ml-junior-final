
# Проект: модель кредитного риск-менеджмента  
## Описание архитектуры и логики решения

Данный файл описывает **актуальный production-flow проекта**  
от загрузки исходных данных до инференса по конкретному пользователю.

Цель проекта — построить модель, оценивающую вероятность дефолта клиента  
на основе агрегированной кредитной истории.

---

## 1. Загрузка и агрегация исходных данных

### Файл: `src/data_loading.py`

Исходные данные представлены в виде нескольких parquet-файлов.  
Один клиент (`id`) может встречаться в данных многократно.

Реализованный подход:
- parquet-файлы читаются **итеративно** (без загрузки всего объёма в память);
- данные агрегируются по `id`;
- для числовых признаков используются агрегаты `mean` и `max`;
- выполняется повторная агрегация для защиты от дубликатов `id`
  между разными файлами.

Результат:
- формируется базовый датасет, где **одна строка = один клиент**;
- датасет передаётся дальше в preprocessing-pipeline.

---

## 2. Preprocessing и объединение с таргетом

### Файл: `src/preprocessing.py`

Вся логика подготовки данных вынесена в production-код.

Pipeline выполняет:
1. загрузку и агрегацию raw-данных;
2. применение Feature Engineering;
3. объединение с целевой переменной `flag` из `train_target.csv`;
4. сохранение итогового датасета в `data/processed/`.

Результат:
- `dataset_with_target.pkl` — используется для обучения моделей;
- `dataset_features.pkl` — используется для инференса.

---

## 3. Feature Engineering

### Файл: `src/feature_engineering.py`

Фичи сгруппированы по логическим блокам.

### Группа A — признаки просрочек
- общее количество просрочек;
- количество длительных просрочек (60+);
- доля длительных просрочек;
- бинарные флаги наличия просрочек;
- максимальная категория просрочки.

**Основной источник сигнала в данных.**

---

### Группа B — отношения к кредитному лимиту
- отношение задолженности к лимиту;
- отношение просрочки к лимиту.

Позволяют нормализовать абсолютные значения и повысить
обобщающую способность модели.

---

### Группы C и D
(платёжная дисциплина и временные признаки)

Были реализованы и протестированы,  
но **не дали прироста ROC-AUC** и исключены из финального pipeline.  
Это зафиксировано в экспериментах.

---

## 4. Эксперименты с моделями (исследовательская часть)

Эксперименты проводились в ноутбуках и **не входят в production-pipeline**.

Протестированы модели:
1. Logistic Regression (baseline);
2. Decision Tree;
3. Random Forest;
4. LightGBM;
5. CatBoost (диагностически).

LightGBM показал наилучшее качество  
после Feature Engineering (группы A + B) и выбран как финальная модель.

---

## 5. Финальный pipeline обучения

### Файл: `src/pipeline.py`

Pipeline реализует **двухэтапное обучение**.

### Этап 1 — валидация
1. загрузка `dataset_with_target.pkl`;
2. stratified train/test split (80/20);
3. обучение модели LightGBM на train;
4. оценка качества по ROC-AUC на test;
5. сохранение test-предиктов.

### Этап 2 — финальное обучение
6. повторное обучение модели **на всём датасете**;
7. сохранение финальной модели.

### Артефакты:
- `artifacts/model.pkl` — **финальная модель (обучена на всём датасете)**;
- `artifacts/predictions.csv` — **предикты на test-выборке** (для отчёта).

### Финальное качество:
- **ROC-AUC (test) = 0.7363**

## 6. Инференс по конкретному пользователю

### Файл: `src/predict.py`

Реализован CLI-инференс.

Логика:
1. загружается финальная модель (`model.pkl`);
2. загружается датасет признаков;
3. пользователю показываются случайные `id`;
4. пользователь вводит `id`;
5. рассчитывается вероятность дефолта;
6. результат интерпретируется текстово.

Пороговые значения:
- < 20% — низкий риск;
- 20–50% — умеренный риск;
- 50–70% — высокий риск;
- > 70% — критический риск.

## 8. Почему ROC-AUC < 0.75

Финальное значение:
- **ROC-AUC (test) = 0.7363**

Ограничения обусловлены:
- агрегированным характером исходных данных;
- отсутствием временных и поведенческих последовательностей;
- сильным дисбалансом классов (~3.5%);
- исчерпанием сигнала на уровне Feature Engineering.

Для дальнейшего роста качества потребовались бы:
- более детальные временные данные;
- транзакционные последовательности;
- поведенческие признаки.

---

## 9. Итог по моделям

- Logistic Regression — baseline;
- Decision Tree — нелинейный, но нестабильный;
- Random Forest — устойчивый ансамбль;
- **LightGBM — финальная модель**;
- CatBoost — диагностический инструмент.

Выбор LightGBM обусловлен лучшим балансом  
качества, скорости и устойчивости на данном датасете.
